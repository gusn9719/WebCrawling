## Phase 2: 뼈대 구조

### @st.cache_data vs @st.cache_resource

처음엔 그냥 둘 다 "캐시"라서 뭐가 다른지 잘 몰랐다.
찾아보니 핵심 차이는 "직렬화 가능 여부"였다.

`@st.cache_data`는 반환값을 피클로 복사해서 세션마다 별도의 사본을 준다.
DataFrame처럼 직렬화되는 객체에 맞다. 반면 `@st.cache_resource`는
복사 없이 하나의 객체를 모든 세션이 공유한다.
모델(joblib 객체, scikit-learn estimator)은 복사하면 불필요하게 무거워지고,
여러 세션이 읽기 전용으로 공유해도 안전하니까 `@st.cache_resource`가 맞다.

실제로:
- 모델 2개 (vec, clf): `@st.cache_resource`
- 144K행 집계 결과 (stats_df, full_df): `@st.cache_data`

### 144K행 예측을 startup에 넣기로 한 이유

처음엔 "그냥 필요할 때만 예측하면 되지 않나?" 싶었다.
근데 탭 1 필터링을 할 때마다 매번 144K행을 TF-IDF 변환하고 예측하면 너무 느릴 것 같았다.
첫 번째 방문자가 5~10초 기다리고, 그 다음부터는 즉시 응답하는 게 맞다고 생각했다.
`@st.cache_data`에 `show_spinner`를 달아서 첫 로딩임을 알려주는 방식으로 처리했다.

### smoke test

App Control Policy 때문에 streamlit.exe 직접 실행이 차단됨.
대신 `ast.parse()`로 구문 검사, Python 스크립트로 데이터 로직 검증으로 대체했다.

## Phase 3: 탭 1 — 상품 추천

### 중요 버그 발견 및 수정

처음에 `clf.predict()`가 "positive", "negative", "neutral" 문자열을 반환한다고 가정했다.
근데 실제로는 `clf.classes_ = [0, 1, 2]` — 정수를 반환한다.

그래서 `(x['pred'] == 'positive').mean()` 이 항상 0이 됐다.
결과로 모든 상품의 positive_rate가 0이 되고,
score는 avg_rating과 review_count만으로 결정됐다.
score range가 23~38로 좁게 나온 것도 이 때문이었다.

수정: `_ID2LABEL = {0: 'negative', 1: 'neutral', 2: 'positive'}` 매핑을 만들고
`pred_ids = clf.predict(...); df['pred_label'] = [_ID2LABEL[p] for p in pred_ids]`로 변환.

수정 후 score range: 55.63 ~ 98.18, avg positive_rate: 0.838 → 맞음.

### 브랜드 목록을 카테고리 필터 이후에 갱신하게 한 이유

카테고리를 "skincare"로 선택했는데 브랜드 목록에 maskpack 브랜드가 섞여 있으면
선택해봤자 빈 결과가 나온다. 사용자 입장에서 당연히 현재 카테고리 브랜드만 보이는 게 맞다.
Streamlit은 위에서 아래로 실행되므로 sel_cat 값이 정해진 다음에 brand_pool을 계산하면 자동으로 연동된다.

### 리뷰 길이 20~300자 제한

너무 짧은 리뷰("좋아요", "별로에요")는 대표 리뷰로 보여줘도 정보가 없다.
너무 긴 리뷰는 카드 UI에 다 담기 어렵고 읽기 불편하다.
20자는 최소 의미 있는 문장 길이, 300자는 화면에 적당한 길이로 잡았다.

### 추천점수 공식에서 negative_rate를 빼지 않은 이유

`score = positive_rate*0.6 + avg_rating/5*0.3 + log_normalized*0.1`

처음엔 negative_rate를 점수에서 직접 빼는 게 맞지 않나 생각했다.
근데 positive_rate + negative_rate + neutral_rate = 1이라서,
positive_rate를 높이면 자연히 negative_rate가 줄어든다.
따로 빼면 negative를 이중으로 패널티 주는 셈이 된다.
대신 사이드바의 "최대 부정률" 슬라이더로 아예 필터링하게 했다.
이쪽이 더 직관적이기도 하고 (사용자가 원하는 기준을 직접 설정).

### 아쉬운 점

실제 UI를 화면에서 확인하지 못했다. 브라우저에서 탭 전환, 필터 조합, 긴 상품명 표시 등
직접 테스트해보지 못한 부분이 많다. App Control Policy 때문인데,
사용자가 직접 `streamlit run`으로 실행해보는 게 필요하다.

## Phase 4: 탭 2 (비교) + 탭 3 (리포트)

### 비교 탭에서 skin_type을 점수 산식이 아니라 보조 분석으로만 쓴 이유

skin_type null이 58%다. 점수에 반영하면 피부타입 정보가 있는 상품만 유리해진다.
정보를 많이 남긴 리뷰어가 있는 상품이 실제보다 더 좋아 보이게 된다.
그래서 점수엔 안 넣고, 비교 탭에서 "이 상품은 건성 피부에 긍정률이 높다" 정도로만 보조 정보로 썼다.

### 모델 리포트 보고 느낀 점

6개 모델 성능 표:

| 모델 | Accuracy | Macro F1 | Neutral F1 | Neutral Prec |
|------|----------|----------|------------|--------------|
| baseline_balanced | 0.9198 | **0.6859** | 0.2820 | 0.1997 |
| baseline_none | 0.9514 | 0.6250 | 0.0511 | 0.4474 |
| lstm_balanced_e3_earlystop | 0.8797 | 0.6606 | 0.2424 | 0.1434 |
| lstm_balanced | 0.8571 | 0.6476 | 0.2215 | 0.1271 |
| lstm_none_e3_earlystop | 0.9501 | 0.6344 | 0.0876 | 0.3875 |
| lstm_none | 0.9501 | 0.6344 | 0.0876 | 0.3875 |

`baseline_none`이 accuracy 0.9514로 가장 높은데,
neutral F1이 0.05밖에 안 된다. 사실상 neutral을 "positive"로 다 예측하는 거다.
accuracy가 높게 나오는 건 그냥 전체 데이터의 86.8%가 positive라서,
항상 positive라고 예측해도 accuracy가 86%가 넘기 때문이다.
이런 걸 "정확도 역설(accuracy paradox)"이라고 하는 것 같다.

`baseline_balanced`가 macro F1이 가장 높아서 전체적으로 가장 균형 잡혔다고 판단.
neutral precision이 0.20이라는 건 모델이 "neutral"이라고 한 것 중 80%가 틀린 것.
그래서 서비스에서 neutral을 "기타/불확실"로 표시하고 항상 경고를 달기로 했다.

### LSTM이 3 에폭만에 early stop된 게 놀라웠다

학습 이력이 3행이다. 에폭 3개에서 val_loss가 올라가서 멈춘 것 같은데,
신경망이 이렇게 빨리 포화되는 게 신기하다.
TF-IDF + 로지스틱 회귀가 macro F1 기준으로 LSTM보다 나은 걸 보면,
리뷰 감성 분류에서 문맥보다 키워드가 더 중요한 게 아닌가 싶다.
"자극", "트러블" 같은 단어가 나오면 거의 부정이고,
"촉촉하다", "재구매" 같은 단어가 나오면 거의 긍정이라서.

## Phase 5: 탭 4 — 리뷰 직접 분석

### session_state로 버튼 → textarea 연동

버튼을 누르면 textarea 값이 바뀌어야 하는데,
처음엔 그냥 `value=st.session_state['input_text']`로 하면 되겠다고 생각했다.
Streamlit은 rerrun 방식이라서 버튼 클릭 → `session_state` 값 수정 → 리렌더링에서 textarea가 새 값 읽기.
key를 따로 지정해서 Streamlit이 내부적으로 충돌 없이 관리하도록 했다.

### KoNLPy fallback의 실제 필요성

이 환경에서는 KoNLPy + Okt가 잘 설치돼 있었다.
whitespace tokenizer로 테스트하면 긍정 예시조차 pos=0.23이 나오는데,
Okt 토크나이저로 하면 pos=1.00이 나온다. 차이가 너무 크다.
학습 때 Okt로 만든 tokens_str을 쓴 것과 예측 시 같은 방법을 써야 한다는 게 중요했다.
fallback을 남겨둔 건 다른 환경에서도 돌아가게 하려고지만,
실제로 Okt 없이 쓰면 의미 있는 예측이 안 된다고 봐야 한다.

### 중립 예시 문장 예측 결과

"그냥 평범해요. 특별히 좋거나 나쁜 점은 없는 것 같아요"
→ pos=0.38, neg=0.01, neu=0.61

Okt로 토크나이징하면 "좋다", "나쁘다"가 둘 다 나온다.
모델 입장에서는 "좋다"와 "나쁘다"가 같은 문장에 있으니 헷갈릴 법하다.
neu=0.61인데, neutral recall이 0.48(baseline_balanced 기준)이라서
neutral을 잘 못 잡는 모델인데도 이 문장은 neutral로 잡은 게 신기하다.
앱에서는 pos>=0.6, neg>=0.4 임계값을 써서 둘 다 못 넘으면 "불확실"로 처리했다.
이 예시는 pos=0.38 < 0.6이고 neg=0.01 < 0.4라서 "판정 불확실"이 나온다 → 적절한 것 같다.

### pos>=0.6, neg>=0.4 임계값을 선택한 이유

긍정 임계값을 0.5가 아니라 0.6으로 높인 건, neutral precision이 낮아서
pos=0.5~0.6 구간의 예측이 실제로는 불확실할 가능성이 높기 때문이다.
부정 임계값을 0.4로 낮춘 건, 부정 리뷰를 더 엄격하게 잡기 위해서다.
상품에 부정적인 내용이 조금이라도 있으면 사용자가 알아야 하는 경우가 많기 때문.
만약 임계값을 neg>=0.5로 하면 neg=0.45 같은 애매한 경우를 놓칠 수 있다.

## Phase 6: 코드 리뷰 및 최종 수정

/code-review 실행 후 7개 문제 발견. 그 중 확인(CONFIRMED) 2개, 개연성(PLAUSIBLE) 3개, 반박(REFUTED) 2개.

### 발견된 버그와 수정 내용

**버그 1 (CONFIRMED): Tab 4 textarea 키 충돌**
`st.text_area(key="user_input_area")`와 `st.session_state["input_text"]`를 따로 쓴 게 문제였다.
Streamlit에서 widget에 key를 지정하면 그 widget 값은 `st.session_state[key]`에 저장되고,
`value=` 파라미터는 초기 렌더링에서만 쓰인다. 그러니까 사용자가 한 번 텍스트박스를 건드리면,
"긍정 예시" 버튼을 눌러도 `st.session_state["input_text"]`만 바뀌고
실제 표시되는 텍스트박스는 `st.session_state["user_input_area"]`를 읽으니까 아무 변화가 없다.
수정: `st.text_area(key="input_text")`로 통일. 버튼이 같은 key에 쓰니까 자동으로 동기화됨.

**버그 2 (CONFIRMED): include_high 체크박스 무효**
가격 슬라이더 max가 `min(price.max(), 200_000)`으로 하드캡이 걸려 있어서,
`apply_filters`에서 200,000 가드를 해제해도 슬라이더 값 자체가 200,000 이하라
`f = f[f["price"] <= price_max]` 이 줄에서 어차피 200K 이상은 걸러진다.
수정: 체크박스를 슬라이더 앞으로 이동. 체크 상태에 따라 `price_ceiling`을 결정.

**버그 3 (CONFIRMED): 이중 joblib 로딩**
`load_and_aggregate()` 안에서 `joblib.load()`를 직접 호출해서 `load_models()`의
`@st.cache_resource` 캐시를 우회하고 있었다. 매 cold start마다 모델을 두 번 읽음.
수정: `vec, clf = load_models()` 한 줄로 교체.

**수정 중 배운 것: `apply_filters`의 `.copy()`**
`stats.copy()`를 하고 있었는데, 이후의 `f = f[f[...]]` 연산들은 모두 새 객체를 반환하니까
원본 `stats`를 건드리지 않는다. `.copy()`가 없어도 안전하다는 걸 코드 리뷰 덕에 알게 됐다.
pandas boolean indexing은 항상 뷰가 아니라 새 DataFrame을 반환하니까.

**3중 groupby.apply → value_counts().unstack()**
세 번의 `grp.apply()`를 한 번의 `value_counts(normalize=True).unstack()`으로 교체했다.
cold start 속도가 개선됨. `reindex(columns=[...], fill_value=0)` 으로
컬럼이 없을 경우 (모든 리뷰가 한 레이블인 상품)도 안전하게 처리.

## 학습 회고

### 오늘 가장 많이 배운 것

`clf.classes_`를 먼저 확인하지 않고 predict() 출력 타입을 가정한 게 버그로 이어졌다.
score range가 23~38로 좁게 나오길래 이상하다고 느꼈는데,
원인을 역추적해서 찾아낸 게 좋은 디버깅 경험이었다.
"결과가 이상하게 작다" → "positive_rate가 0이다" → "비교가 항상 False다"
→ "predict()가 정수를 반환한다"의 흐름으로 찾아냈다.

Streamlit의 캐싱 전략도 배웠다.
객체 공유 여부가 cache_resource vs cache_data 선택 기준이라는 게 처음엔 잘 안 와닿았는데,
"여러 사용자가 같은 모델 객체를 동시에 읽기만 한다면 복사가 불필요하다"는
관점으로 이해하니까 명확해졌다.

### 다음에 개선하고 싶은 것

1. 실제 UI 테스트: App Control Policy 때문에 시각적으로 확인하지 못했다.
   사이드바 필터가 실시간으로 잘 반응하는지, plotly 차트가 올바르게 렌더링되는지 확인 필요.

2. 리뷰 카드 개선: 현재 대표 리뷰를 그냥 텍스트로만 보여주는데,
   리뷰어 정보(피부타입, 별점 등)를 함께 표시하면 더 유용할 것 같다.

3. 검색 기능: 탭 2 상품 비교는 multiselect에서 검색이 가능하긴 한데,
   탭 1에서 상품명 직접 검색이 안 된다. 브랜드명 검색 기능이 있으면 좋겠다.

### neutral 성능 한계를 다룬 방식이 적절했는지

전반적으로 적절했다고 생각한다.
neutral을 "기타/불확실"로 이름을 바꾸고, 모든 곳에 precision 0.20 경고를 달았다.
다만 한 가지 고민은: 이 경고가 너무 자주 보이면 사용자가 무시하게 된다.
"neutral 경고를 접을 수 있는 expander 안에 넣는 게 낫지 않을까?"라는 생각도 든다.
지금은 명세대로 항상 표시하게 했다.

### Streamlit 처음 써보면서 어려웠던 것

re-run 방식이 처음엔 직관적이지 않았다. 버튼을 눌러도 "그 자리에서" 뭔가가 바뀌는 게 아니라
전체가 위에서 다시 실행되는 거라서, 상태를 유지하려면 `session_state`를 써야 한다는 게 낯설었다.
특히 버튼 → textarea 연동에서 이게 중요했다.
탭 안에 넣은 코드도 모든 탭이 다 실행되는 것 같은데, 이게 성능에 얼마나 영향을 주는지 궁금하다.
